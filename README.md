# yet-rs

A Rust port of the Python `yet_zero` eye-tracking experiment runner.

> **Status:** Sprints 0–5 (foundations, risk spikes, experiment model,
> scheduler/headless slice, CV features and model, camera and calibration). The
> workspace runs a two-block experiment without a window, writes a
> yet_zero-compatible result CSV, captures the real Yet camera on Linux and runs
> a graphical calibration on the presenter monitor. Feature extraction and the
> linear gaze model are verified against NumPy, OpenCV and scikit-learn on
> committed synthetic fixtures. The full presenter and console are still ahead.

## What it will do

- Present static images and pre-decoded video clips on a chosen monitor.
- Calibrate a webcam-based tracker from four quadrant-brightness features.
- Drive experiments from a separate experimenter console.
- Draw a click-through gaze overlay over the desktop.
- Write trial and frame data to CSV for the existing R pipeline.
- Run on Windows, macOS and Linux without OpenCV or a C/C++ toolchain.

## What exists now

- `yet-present` — `SessionTime`, physical-pixel geometry, `Scene`/`DrawCommand`,
  presenter/overlay/media/audio traits, and a `RecordingPresenter`.
- `yet-core` — a pure `step` engine with start/pause/resume/abort/tick,
  absolute trial deadlines, late-tick accounting, a `TestClock`, and the
  calibration data types.
- `yet-core` — experiment/config loading from `config.toml`, `Experiment.csv`
  and `Stimuli.csv`, typed validation, resolved media paths and deterministic
  per-block trial planning.
- `yet-core` — a calibration grid (3×3 at 0.125/0.5/0.875), stimulus placement
  and golden scenes, plus a yet_zero-compatible CSV data sink with flush per
  trial.
- `yet-core` — `GrayFrame`/`EyeRegion`, canonical `quad_brightness` with the
  odd-dimension split rule, Rec. 601 luma matching OpenCV, and a
  `LinearGazeModel` (centered SVD least squares) with a calibration buffer and
  Euclidean RMSE. Python-oracle parity is checked by
  `crates/yet-core/tests/cv4_parity.rs`; fixtures are generated by
  [`tools/cv4_fixtures.py`](tools/cv4_fixtures.py) and documented in
  [`docs/fixtures/CV-4.md`](docs/fixtures/CV-4.md).
- `yet-core` — camera capture behind `Camera`: `linuxvideo` on Linux,
  `nokhwa` on macOS/Windows, a dedicated capture thread with a latest-frame
  mailbox, YUYV/GRAY/MJPEG conversion and capture statistics. The calibration
  flow records target/feature pairs, fits or refits without a session restart,
  and reports RMSE.
- `yet-app` — `yet-app plan <experiment-dir>` prints the resolved session plan.
- `yet-app` — `yet-app run --headless <experiment-dir>` drives a full session
  with a synthetic monotonic clock and writes the result CSV. Without a camera
  there are no gaze samples yet, so the file contains the header only.
- `yet-app` — `yet-app camera <experiment-dir>` measures a real camera and can
  dump the raw eye ROI. `yet-app calibrate <experiment-dir>` opens a graphical
  calibration window on the presenter monitor: the 3×3 grid, automatic frame
  collection, RMSE report, quick recalibration and a live gaze dot. `--terminal`
  keeps the coordinate-printing fallback.
- CI for Linux, macOS and Windows, plus a Rust 1.88 MSRV check.
- Sprint 1 risk reports in [`docs/spikes/`](docs/spikes/) covering eframe
  presentation, the overlay matrix, camera capture/parity and media/audio.

## Build

Requires Rust 1.88 or newer.

```sh
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo doc --workspace --no-deps
cargo run -p yet-app -- plan examples/demo
cargo run -p yet-app -- run --headless examples/demo --participant demo01
cargo run --release -p yet-app -- camera examples/demo --seconds 3
cargo run --release -p yet-app -- calibrate examples/demo --quick
cargo run --release -p yet-app -- calibrate examples/demo --terminal
```

## Headless runs

`yet-app run --headless` needs no window and no display. It walks the plan
with a 10 ms synthetic clock: each tick jumps to the next frame step or trial
deadline, so a five-trial demo finishes in milliseconds. Output:

```text
Result: examples/demo/yet1_demoMartin_demo01.csv
Trials: 5 of 5 completed
Samples: 0
```

Use `--output <csv>` to choose the result path. `--participant` defaults to
the Unix time at session start, as in the Python prototype. The headless runner
does not open the camera yet, so the result file contains only the schema
header; live capture is exercised by the `camera` and `calibrate` commands. The
trial scheduler and protocol wiring are still exercised end to end.

### Result CSV

Columns are exactly `Exp,Part,Stim,time,x,y,x_pro,y_pro`, matching yet_zero.
`Exp` concatenates the experiment id and the experimenter, `Part` is the
participant id, `x`/`y` are gaze coordinates in stimulus pixels, and
`x_pro`/`y_pro` are normalized to the stimulus size. Times are epoch seconds
with microsecond precision. Every trial boundary flushes the file, so an
aborted session keeps the completed trials.

## Camera and calibration

The experiment config carries the display geometry and the camera:

```toml
[display]
presenter_monitor = 1
console_monitor = 0
width = 1440
height = 2560
fullscreen = true
presenter_origin = [2560, 0]   # presenter monitor origin in desktop pixels

[camera]
usb_index = 2                 # the GEMBIRD/Yet camera on this workstation
width = 640
height = 480
fps = 30
format = "yuyv"               # auto, gray, yuyv or mjpeg
eye_region = [0.25, 0.25, 0.5, 0.5]   # normalized x, y, width, height
```

The Yet camera is the **GEMBIRD/AppoTech UVC** device on `/dev/video2`; it
advertises YUYV only at 640×480 and sustained 25.6 fps in the SPK-5 measurement.
`/dev/video0` is the StreamCam, which is faster in MJPG but is not the tracker
camera. Device indices can move across reboots; check the names in
`/sys/class/video4linux/` or override a run with `--device N`.

```sh
# Measure the camera, print format/fps/statistics and the last quadrant means.
cargo run --release -p yet-app -- camera examples/demo --seconds 3
cargo run --release -p yet-app -- camera examples/demo --device 0 --seconds 3

# Also write the raw eye ROI as an 8-bit grayscale file for CV-4 parity.
cargo run --release -p yet-app -- camera examples/demo --save-roi /tmp/eye.gray

# Graphical calibration on the presenter monitor (default).
cargo run --release -p yet-app -- calibrate examples/demo --quick

# Terminal fallback for headless machines.
cargo run --release -p yet-app -- calibrate examples/demo --terminal
```

The graphical calibration opens a borderless window sized to the configured
presenter area. Press **Space** to start and **Escape** to cancel. Each orange
target is shown for 800 ms, then frames are collected automatically; the RMSE
appears for 2 s, then `--quick` adds a center-target refit. With `--skip-live`
the window closes after the report; otherwise a red dot follows the prediction
for `--live-seconds`.

`presenter_origin` is in desktop physical pixels. It is needed on X11 because
eframe 0.33 cannot select a monitor by index; it also works on Windows and
macOS. On Wayland, leave it unset: the compositor chooses the screen. The demo
values target a portrait 1440×2560 presenter at `+2560+0`; adjust them for
another layout (`xrandr --query` lists the origins on X11). Calibration targets
are fitted in the window's actual physical pixels, so the model, the drawn grid
and the live dot stay consistent even if the window manager adjusts the window.

**MSRV tradeoff:** eframe 0.37 offers `ViewportBuilder::with_monitor` but
requires Rust 1.95. The project keeps Rust 1.88 and uses eframe 0.33 with the
origin workaround. The full presenter in Sprint 6 should revisit this choice.

Platform notes:

- **Linux:** the user must be able to read `/dev/videoN` (usually the `video`
  group). `linuxvideo` needs no C toolchain.
- **Windows:** camera privacy settings must allow desktop apps; nokhwa uses the
  Media Foundation backend.
- **macOS:** install Xcode Command Line Tools, allow camera access when TCC
  prompts, and expect the permission dialog on first use. The macOS runtime is
  not yet tested here.

See [`docs/spikes/SPK-5.md`](docs/spikes/SPK-5.md) for the measured Linux
results, the two-monitor geometry and the open hardware checks.

## Experiment format

An experiment directory contains three files:

- `config.toml` — machine settings (monitors, camera, presenter, overlay, audio).
- `Experiment.csv` — optional key/value metadata: `id`, `experimenter`,
  `instructions`, `shuffle`, `seed`. If `shuffle` is true, `seed` is required.
- `Stimuli.csv` — rows with `id`, `kind` (`image` or `sequence`), `path`,
  `fps`, `duration_ms`, `loop`, `audio`, and an optional `block`.

Paths are resolved relative to the experiment directory. Images must exist and
must not set `fps`, `loop=true`, or `audio`; sequences require `fps`. Rows without a
`block` form a `default` block. Trials are shuffled within each block; block `i`
uses `seed + i`, so the plan is reproducible.

See [`examples/demo`](examples/demo) and run:

```sh
cargo run -p yet-app -- plan examples/demo
```

## Design

- The engine is independent of any UI. `step(state, event, now)` returns
  effects; the application executes them.
- Protocol coordinates are monitor-local physical pixels.
- Protocol messages carry media identifiers and owned text, never image buffers.
- `yet-core` and `yet-present` must not depend on a windowing toolkit.

The reasoning behind these choices is in
[`DEVELOPMENT_PLAN.md`](DEVELOPMENT_PLAN.md),
[`UI_analysis.md`](UI_analysis.md) and [`CV_analysis.md`](CV_analysis.md).
